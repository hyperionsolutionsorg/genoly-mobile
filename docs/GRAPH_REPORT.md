## 1. Project overview (30-second picture)

`genoly-mobile` is the **mobile app repository** for the Genoly product family. One unified Expo React Native app, cross-platform iOS + Android. **Fitness is the first filled section** — future sections (family tree mobile, atlas mobile, etc.) will land in the same app over time.

Hyperion Solutions LLC. The mobile app talks to the **shared Convex backend** in the separate `../genoly-family-web/` repo. Forkability invariant means the mobile app can flip to a standalone fitness-only deployment in the future with minimal changes (Convex URL constant + brand strings only).

**Hard rule, non-negotiable:** mobile apps are **FREE with NO in-app payments**. The web (`genoly.org/billing`) is the sole subscription surface. This avoids Apple's 30% cut and App Store anti-steering risk. Server returns `isPaymentNeutral: true` as a tripwire; mobile UI must check this before rendering anything subscription-related (see AGENTS.md §3.1).

## 5. Planned packages (Phase 1 implementation targets)

These are the three workspace packages that will hold the load-bearing mobile code. Currently `.gitkeep`-only placeholders.

### 5.1 `packages/api-client/` — typed fitness API + offline queue

**Will implement** the 20 fitness HTTP endpoints (per `../genoly-family-web/docs/fitness-api-contract.md`) with:
- Token storage via `expo-secure-store` (under key `fitness.bearerToken` — see AGENTS.md §3.4)
- Per-method retry policy: GET = exponential backoff (0s, 1s, 3s + jitter, max 3); 429 = honor `Retry-After`; POST/PUT/DELETE = **no auto-retry** (user must retry explicitly to avoid double-write ambiguity — see AGENTS.md §3.5)
- 401 hard-teardown flow: cancel in-flight requests, clear token, wipe SQLite queue, wipe Zustand, navigate to login (AGENTS.md §3.6 — 7 steps)
- Offline write queue in `expo-sqlite` with retry policy + clock-drift defense
- ApiClient base URL injected via `ApiClientConfig.baseUrl` from app environment (never hardcoded — forkability concern, AGENTS.md §3.10)

**Files (planned):** `src/{index,client,tokenStore,queue,types}.ts`. Public API surface: `ApiClient` class with methods matching the 20 endpoints. Auth helpers exported separately.

### 5.2 `packages/health-sync/` — HealthKit + Health Connect adapter

**Will implement** an isolation barrier between the rest of the app and the platform-specific health APIs.

- **Isolation rule (HARD):** code that touches HealthKit / Health Connect lives ONLY here. Screens never import the platform APIs directly. The `HealthAdapter` interface (defined in `packages/health-sync/index.ts`) hides platform divergence.
- iOS: `react-native-health` via Expo config plugin
- Android: `expo-health-connect`
- Initial historical pull on first permission grant: **30 days** (bounded — see AGENTS.md §3.7)
- Partial-permission grants are legitimate: render zeros for unavailable metrics, no error states

### 5.3 `packages/types/` — shared types

**Will mirror** the TypeScript types from `../genoly-family-web/docs/fitness-api-contract.md` so both server and mobile speak the same vocabulary. Includes the `isPaymentNeutral: true` tripwire literal type.

## 8. Hard rules (mobile-specific)

These are codified in AGENTS.md but worth surfacing here because they're load-bearing.

1. **Mobile payment neutrality (AGENTS.md §3.1).** NO in-app payments. Subscriptions only via web. The `useSubscription` hook THROWS if server's `isPaymentNeutral` is ever false — preferring hard fail in dev over App Store rejection in prod.
2. **Native module strategy (AGENTS.md §3.2).** Expo modules only. NO bare workflow. If a capability has no Expo module, write an Expo config plugin before considering ejecting.
3. **Health-reading isolation (AGENTS.md §3.3).** Platform health APIs only touched in `packages/health-sync/`. Screens never import HealthKit or Health Connect directly.
4. **Bearer token storage (AGENTS.md §3.4).** Only `expo-secure-store`. Never AsyncStorage. Never plaintext logs. Three operations: `getBearerToken`, `setBearerToken`, `clearBearerToken`. Wrap in `packages/api-client/src/tokenStore.ts`.
5. **Forkability impact (AGENTS.md §3.10).** ANTI-PATTERN: never hardcode the Genoly Convex URL inside `packages/api-client/`. URL is injected via `ApiClientConfig.baseUrl` from app environment.
6. **Background sync constraints (AGENTS.md §3.8).** `expo-background-fetch` with `minimumInterval: 15 * 60` (OS-enforced floor). Each wake: <10 seconds total. Killed-app behavior: iOS terminates user-swiped apps — document in Settings FAQ.
7. **Clock-drift defense (AGENTS.md §3.9).** Mobile clocks are untrusted. Server `serverTime` from `POST /api/fitness/sync/daily` is authoritative. Compute `clientServerSkew = serverTime - Date.now()` on every successful sync.

## 9. Forkability impact

When fitness extracts to its own deployment (per `FORK_PROCEDURE.md`), the mobile app changes **minimally**:

- Convex base URL constant flips
- Brand strings change (if new product brand)
- All packages work unchanged

The anti-pattern to avoid: hardcoding the Genoly Convex URL anywhere in `packages/api-client/`. URL must always be injected via `ApiClientConfig.baseUrl`.
